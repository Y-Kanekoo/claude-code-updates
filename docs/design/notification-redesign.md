# 通知・レポート再設計（2026-09-26）

## 解決する問題

2026-09-25のActionsは、v2.1.280の114項目をまとめた入力がGroqの上限に達し、HTTP 413で停止していた。429だけを利用制限として扱っていたため、利用者には原因のわからない同じ失敗通知が毎日届いていた。

以前の通知は保存前後の工程が混在しており、Discordの送信失敗をチェックポイントから再試行できなかった。レポートの全セクションを通知に転記し、HTMLコメントや未公開のスライドリンクを含むこともあった。

## 新しい処理

1. 公式ノートに安定した根拠IDを付け、6項目・約4,500バイトを目安に分割する。出力を3,072トークンに制限する。
2. 各分割の全項目・分類・識別子・根拠IDを検証する。分割結果はモデル・原文・指示版のハッシュで保存し、途中停止後に再利用する。
3. 413は同じ入力の再送では解決しないため、変更項目の境界でさらに二分する。1項目が単独でも上限超過の場合は原文を保持する。429・認証エラー・モデル利用不可は区別する。
4. 日本語レポートと送信待ちを保存してからチェックポイントを進める。部分進捗とキャッシュもGitに保存する。
5. レポート公開の成功を確認した後、送信待ちを古い順に送る。期限通知はレポート公開に依存させない。
6. Discordの `wait=true` によるメッセージIDを確認して送信済みにする。送信済みは再実行で送らない。429は指定の待機時間（最大30秒）を守り、上限超過は次回へ持ち越す。
7. 同一障害は原因と対象バージョンで識別し、初回・7日後・原因変更時だけ通知する。障害後に生成・公開・送信が成功したら復旧を一度通知する。

## 読みやすさ

新規レポートは第3版と明示し、要約・判定・推奨対応・影響範囲を冒頭へ移す。判定は表1つにまとめる。原文にない移行作業や任意設定の必須化は勧めない。根拠コメントを保った詳細を後ろに置き、関連リンクは最後にまとめる。原文へのフォールバックは暫定レポートと表示する。

通知は要約と最大3件ずつの対応・対象・主な変更を表示し、レポートへのリンクで詳細へ誘導する。メンションを無効にし、コメントは表示しない。UTF-16換算でフィールドと全体がDiscordの文字数制限内に収まる長さにする。

旧レポートは履歴として維持する。パーサーは旧形式と第3版を認識するが、新規生成は第3版を正とする。

## 状態と復旧

- `last-checked.json`: レポート生成が完了したバージョン。
- `notification-state.json`: 未送信、送信済みメッセージID、通知済み障害。シークレットやWebhook URLを含めない。
- `summary-cache/`: 完了した分割要約。レポート保存後にそのリリースのキャッシュを削除する。

導入時は状態ファイルを自動作成する。既存の全レポートを一斉に再通知せず、新しく生成したレポートから管理する。壊れた通知状態は勝手に初期化しない。Gitの直前の正常なファイルを復元する。

送信後、Gitへのpush前に `notification-checkpoint` 成果物を90日間保存する。次回実行の最初に、同じworkflow・branchの直近20回の完了実行から最新の成果物を取得し、送信済みIDと新しい障害状態を復元する。未公開のレポートへの通知を送らないよう、成果物の未送信キューは復元しない。復元に失敗した場合は、重複送信を防ぐため通知を停止する。

生成途中の成果物も失敗時に `report-preview` へ7日間保存する。Discordへの送信成功とGit・成果物への状態保存は別システムのため、両方の保存前に実行が強制終了した場合の重複可能性は残る。未確認の通知を送信済みと推定して欠落させることはしない。

## 検証

既存テストを変更せず、実際のv2.1.280を回帰データとして使う。入力分割と全項目保持、413の再分割、途中再開、送信失敗後の再送、公開前送信の抑止、同一障害の抑制、復旧通知、絵文字を含む長文、スキーマ互換を確認する。`dry_run` は本番APIで生成し、公開と通知を伴わず成果物を確認できる。
